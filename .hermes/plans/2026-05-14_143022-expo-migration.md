# WebToApp Expo Migration Plan

**Date:** 2026-05-14  
**Objective:** Migrate native Android WebToApp to Expo (React Native) for cross-platform (iOS + Android) deployment without requiring Android Studio

---

## 🎯 Goal

Transform WebToApp from a native Android Kotlin/Jetpack Compose application into a React Native + Expo app that:

- ✅ Runs on both Android and iOS from a single codebase
- ✅ Uses Expo Go for instant development/testing (no Android Studio required)
- ✅ Preserves core functionality: URL → app wrapping, media conversion, HTML packaging
- ✅ Maintains extension module system (JavaScript injection)
- ✅ Supports built-in modules and AI-powered features
- ✅ Enables one-click builds via EAS Build (or local standalone apps)
- ✅ Keeps sample projects and templates

---

## 📊 Current State Analysis

### Technology Stack (Current)
- **Platform:** Native Android (Kotlin)
- **UI:** Jetpack Compose (Material 3)
- **Web Engine:** Android WebView + optional GeckoView
- **Build System:** Gradle + CMake (C++ native components)
- **Target:** Android 6.0+ (API 23-36)
- **Native Features:**
  - WebView with injection (extensions)
  - Download manager
  - Notifications
  - Storage & media access
  - Camera/Microphone/Bluetooth/NFC
  - Location services
  - Background services (music playback, forced run)
  - APK signing & building
  - AI integration (LLM APIs)
  - Cloud services (activation, analytics)

### Architecture Overview
1. **ShellActivity** - Standalone WebView runtime (for built APKs)
2. **MainActivity** - App builder UI (Jetpack Compose)
3. **Extension System** - Userscript injection via WebView
4. **Project System** - Asset-based web projects stored locally
5. **Build Pipeline** - Package web assets into signed APKs

---

## 🔄 Migration Strategy

### Approach: **Hybrid Progressive Migration**

We will **NOT** do a big-bang rewrite. Instead:

**Phase 1 (MVP - Expo Shell Runtime):** Build a barebones Expo app that runs existing web projects in a WebView. This becomes the "Expo Go" test target immediately.

**Phase 2 (Builder UI Rewrite):** Rebuild the app builder interface in React Native, matching existing functionality incrementally.

**Phase 3 (Feature Parity):** Implement all native features using Expo modules and custom native code where needed.

**Phase 4 (iOS Support & Polish):** Full iOS compatibility and production readiness.

## 📋 Detailed Implementation Plan

### **Phase 1: Expo Shell Runtime (Weeks 1-3)**

**Goal:** Create a minimal Expo app that can load web projects in a WebView.

**Rationale:** Get immediate value - developers can test their web projects on device via Expo Go while builder UI is being rebuilt.

#### Deliverables

1. **Initialize Expo Project**
   ```bash
   npx create-expo-app@latest WebToAppExpo --template blank-typescript
   cd WebToAppExpo
   npx expo install react-native-webview
   ```
   **Files created:**
   - `package.json`
   - `app.json` / `app.config.js`
   - `tsconfig.json`
   - `expo-env.d.ts`

2. **Implement Core Shell** (`App.tsx`)
   - Wraps existing sample projects from `app/src/main/assets/sample_projects/`
   - Uses `react-native-webview` to load local HTML/CSS/JS
   - Basic navigation: project list → WebView
   - Minimal UI: header, project grid, back button

3. **Local File Serving**
   - Expo cannot directly access `file://` paths in WebView
   - Two options:
     - **Option A (Recommended):** Package sample projects in app bundle (`assets/`) and use `expo-asset` to serve via `expo-file-system`
     - **Option B:** Spin up local HTTP server on device port 3000+ using `expo-file-system` + `expo-network`
   - **Decision needed:** Choose approach (see Open Questions)

4. **Persist Created Projects**
   - Create projects directory using `expo-file-system`
   - Save user-created projects as JSON metadata + assets
   - Simple list view of created apps

5. **Test with Expo Go**
   - Scan QR code → immediate testing
   - Basic interaction: open URL, load local HTML, media gallery

**Success Criteria:**
- Expo Go can display a sample web app (e.g., React demo, Vite vanilla)
- User can create a new "app" by entering URL + name + icon
- Basic list of created apps (persisted locally)

**Estimated Time:** 2-3 weeks (part-time)

### **Phase 2: Builder UI Rewrite (Weeks 4-8)**

**Goal:** Replicate the full app creation/builder interface in React Native.

#### Screens to Implement

1. **Home Screen** - Project list, create new, settings
2. **Create App Wizard** - Multi-step:
   - URL input (or local HTML import)
   - App metadata (name, icon, package name, version)
   - Feature toggles (splash screen, BGM, translation, etc.)
   - Extension module selection
   - Build/Export
3. **App Detail Screen** - Edit settings, preview, rebuild, share
4. **Extension Browser** - View/import built-in modules + templates
5. **AI Assistant** - LLM-powered module generation
6. **Theme Settings** - Dark mode, accent color

#### UI Components (from Jetpack Compose → React Native)

**Port directly:** ~210 Composable functions → React Native components.

**Recommended libraries:**
- `react-native-paper` (Material 3) or `tamagui` / `native-base`
- `react-navigation` (stack + drawer + bottom tabs)
- `react-native-reanimated` (animations)
- `react-native-gesture-handler` (swipe/drag)

**Libraries to evaluate:**
| Compose Pattern | RN Equivalent | Notes |
|----------------|---------------|-------|
| `@Composable` + `mutableStateOf` | React `useState` hooks | Direct mapping |
| `Scaffold` + `TopAppBar` | `react-native-paper` `Appbar` | Material 3 theme |
| `LazyColumn` / `LazyRow` | `FlatList` | Virtualization |
| `Modal` / `AlertDialog` | `Modal` component or library | Reusable |
| `rememberLauncherForActivityResult` | Expo's `expo-document-picker`, `expo-image-picker` | Permissions handled by Expo |

#### State Management

**Keep it simple:** React Context + useReducer or Zustand (recommended). Minimal - project config is JSON.

#### Data Model

Project config as JSON:
```json
{
  "id": "uuid",
  "name": "My App",
  "url": "https://example.com",
  "icon": "base64 or asset URI",
  "packageName": "com.example.app",
  "version": "1.0.0",
  "features": {
    "splash": true,
    "bgm": false,
    "translation": false,
    "extensions": [...]
  }
}
```

**File Storage:** Use `expo-file-system` to persist JSON + assets.

**Success Criteria:**
- Full builder UI functional (create/edit apps)
- Extension picker with built-in modules displayed
- Settings screen with theme toggle
- 80% feature parity with original UI

**Estimated Time:** 4-5 weeks

### **Phase 3: Feature Parity Implementation (Weeks 9-14)**

#### Native Feature Mapping

| Feature | Android Native | Expo / React Native | Notes |
|---------|----------------|---------------------|-------|
| **WebView rendering** | Android WebView | `react-native-webview` (already) | ✅ Done in Phase 1 |
| **JS/CSS injection** | WebView `addJavascriptInterface` | `injectedJavaScript` prop | Direct mapping |
| **Download manager** | `DownloadManager` | `expo-document-picker` + `expo-file-system` | May need custom native module |
| **Notifications** | `NotificationManager` | `expo-notifications` | ✅ Expo provides |
| **Storage (files)** | `MediaStore` + SAF | `expo-file-system` + `expo-media-library` | ✅ |
| **Camera** | `CameraX` | `expo-camera` | ✅ |
| **Microphone** | `AudioRecord` | `expo-av` (audio recording) | ✅ |
| **Location** | `FusedLocationProvider` | `expo-location` | ✅ |
| **Bluetooth** | `BluetoothAdapter` | `expo-bluetooth` (limited) | May need custom module |
| **NFC** | `NfcAdapter` | `expo-nfc` | ✅ |
| **Background music** | `MediaPlayer` + Service | `expo-av` + `expo-task-manager` | ✅ with caveats |
| **APK signing** | Java Keystore | EAS Build credentials | Use Expo Application Services |
| **App building** | Gradle + APK bundling | EAS Build / `expo-dev-client` | Major change |
| **GeckoView (Firefox)** | Mozilla embed | Not supported | Will drop, WebView only |

#### Critical Implementation Tasks

1. **Extension Injection Engine**
   - Store user scripts locally (JSON)
   - Inject on WebView load via `injectedJavaScript`
   - Support dynamic toggle on/off
   - URL matching rules (wildcards/regex)

2. **Build Pipeline Redesign**
   - **Old:** Generate signed APK locally via Gradle
   - **New:** Use **EAS Build** (cloud) OR standalone app generation:
     - Publish custom development client (`expo run:android` / `expo run:ios`)
     - For end users: Build standalone app via `eas build --profile production`
     - Share via TestFlight (iOS) / Play Store (Android) or direct APK download

3. **Project Asset Management**
   - Store user-created projects in app's documents directory
   - Web assets extracted from ZIP/URL
   - Icons stored as images

4. **AI Features**
   - LLM calls remain the same (REST API)
   - Frontend: build module in React Native, send prompt, parse response
   - No changes needed to backend logic

5. **Cloud Services Integration**
   - Activation codes: same crypto (AES-256) via `expo-secure-store`
   - Analytics: collect via custom events or Firebase
   - Webhooks: `expo-network` for callbacks

6. **Offline Mode & Isolation**
   - Use `expo-file-system` for cache
   - Each project isolated via separate WebView state (easier than Android services)

**Success Criteria:**
- All user-accessible features functional
- Extensions working (script injection + CSS)
- Downloads saved to device gallery/downloads
- Notifications triggered correctly
- Background music plays with app in background

**Estimated Time:** 5-6 weeks

## ⚠️ Risks & Trade-offs

### Major Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| **EAS Build dependency** | Requires Expo account, build queue | Offer self-hosted build option or local `eas-cli` |
| **iOS APK building removed** | Users expect APK builds on iOS | Clear docs: iOS builds are IPA via EAS |
| **Native module gaps** | Some hardware features may not work | Write custom native modules (Expo config plugins) |
| **App size increase** | Expo runtime ~15-25 MB | Acceptable trade-off; needed for cross-platform |
| **Loss of custom WebView kernel** | GeckoView not available in Expo | Document limitation; may write native module later |
| **Background service limitations** | iOS restrictive on background tasks | Use `expo-task-manager` + background modes; document limits |

### Trade-offs Made

- **Drop C++ native code:** CMake/NDK components removed. If needed (e.g., crypto acceleration), re-implement in JS or write Expo config plugin.
- **Drop local APK signing:** EAS Build handles signing in the cloud. Advanced users can still self-sign via `eas build --profile local`.
- **Drop multi-arch APK:** Expo builds per-platform binaries automatically.
- **Simplify extension system:** Chrome extension support may be limited; focus on userscripts first.

## 🔍 Open Questions & Decisions Needed

### Q1: Local HTTP Server vs. Asset Bundling for Sample Projects?
**Context:** Original app serves sample projects via local HTTP server (PHP/Go/etc.). Expo WebView cannot load `file://` URLs with all features.

**Option A:** Bundle all sample projects as Expo assets in `assets/` and serve via `expo-asset` + custom file:// to http:// proxy.
- ✅ Faster dev, no server maintenance
- ❌ Limited to static files only (no dynamic PHP/Node)

**Option B:** Start lightweight Node.js/Go server inside Expo app using `expo-task-manager` + background process.
- ✅ Full dynamic sample projects
- ❌ Complex, may not be feasible on iOS (background restrictions)

**Recommendation:** Choose **Option A** - pre-package sample projects as static exports. For dynamic ones (PHP, Node, Python), provide instructions to run externally and load via URL.

---

### Q2: Build Pipeline: Expo Development Client or EAS Build?
**Context:** Original app builds APKs locally. Expo has two modes.

**Option A: EAS Build (recommended)**
- Cloud builds, CLI-only, shareable links
- Apple/Google store compatible
- No local SDK installation
- Cons: Requires Expo account, build queue

**Option B: Custom Development Client**
- `expo run:android` / `expo run:ios`
- Build locally with Xcode/Android Studio
- Closer to original experience but still Expo
- Cons: Still requires SDKs for full local builds

**Recommendation:** **EAS Build** for production builds. For development, use Expo Go (no build step). This aligns with "no Android Studio needed" goal.

---

### Q3: Expo Router vs. React Navigation?
**Decision:** Use **Expo Router** (file-based) if you like Next.js-style routing. Simpler, less boilerplate. Alternative: `react-navigation` (more control). **Recommend Expo Router** for faster navigation setup.

---

### Q4: Keep Android app while migrating?
**Decision:** Yes. Maintain `android/` branch for existing users while Expo version matures. Eventually sunset or offer parallel.

---

### Q5: Handle APK encryption (AES-256)?
**Context:** Original app encrypts APKs with AES-256. With Expo, APKs are built in cloud.

**Options:**
1. Keep encryption metadata in project JSON, build via EAS
2. Provide encrypted download package, user provides key at build time
3. Drop encryption (cloud builds trusted)

**Recommendation:** Option 1 - metadata-only. Build remains in Expo cloud (trusted). Document security model change.

## 🧠 Notes

- **Migration philosophy:** Gradual, parallel development. Don't break existing Android users until Expo version is ready.
- **Data portability:** Project JSON files from old version importable to new (export/import feature).
- **Devices:** Test on low-end and high-end Android, iPhone 13+, iPad.
- **Performance:** WebView is memory-heavy. Add warnings for users creating many concurrent apps.
- **Expo Go limitation:** Some native modules only work in custom dev client, not Expo Go. Plan for stub implementations in Go.
